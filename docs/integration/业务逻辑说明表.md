## 3. 数据源改造整体逻辑

| 步骤 | 逻辑说明 | 当前实现方式 | 关键风险 / 后续方向 |
|---|---|---|---|
| 1. 不复制中台数据源 | SQLBot 不把中台数据源长期同步成本地 `core_datasource`。 | 运行时通过虚拟 Assistant 远程拉取。 | 降低密码二次落库风险，但依赖中台接口稳定性。 |
| 2. 中台返回真实表结构 | 中台返回已登记物理表、字段说明、表描述等元数据。 | `/openapi/sqlbot/datasources/query` 返回 `datasources -> tables -> fields`，其中 `tables` 必须是可执行 SQL 的真实物理表。 | 元数据可见不等于数据可查；目录接口不能替代权限接口。 |
| 3. SQLBot 用表结构做相关性判断 | LLM 基于 M-Schema 判断用户问题与哪些真实表相关。 | 复用 SQLBot 原 `select_datasource`、M-Schema、`generate_sql` 流程。 | 如果只返回资源目录或字段缺失，LLM 会把目录误当物理表，导致生成不可执行 SQL。 |
| 4. 生成 SQL 后校验权限 | 只有当 SQL 涉及的表具备查询权限时才允许执行。 | 调中台 `/openapi/sqlbot/table-permissions/check`；中台按 `dmgt_table -> dmgt_category -> dmgt_role -> dmgt_user_role` 校验表级角色。 | 当前只做表级拦截，不按字段权限表判断；SQLBot 传表名即可完成本阶段 Gate。 |
| 5. 无权返回申请入口 | 如果相关表无权限，SQLBot 返回无权表和申请入口。 | 权限接口响应 `deniedTables[].tableId/categoryId/categoryName/applyUrl`，SSE 透传给前端；嵌入中台时前端优先派发 `sqlbot-message` 打开中台申请弹窗。 | 申请弹窗依赖 `categoryId` 作为 `resourceIds`，权限接口必须稳定返回该字段；独立运行时继续用 `applyUrl` 兜底。 |
| 6. 执行前二次兜底 | 防止 SQL 在过滤、改写、修复后新增表绕过权限。 | Gate 2 在 execute 前复核最终 SQL。 | 需要持续覆盖 join、CTE、子查询、schema.table 等解析场景。 |
| 7. 统一逻辑 datasource | 用户不再选择真实 datasource，SQLBot 在全域表目录中自动路由。 | `route_logical_datasource` 先选相关表；若单源则设置本次 record 的真实 datasource；若跨源则 SSE 返回 `cross_source_not_supported`。 | 一期不做跨源拼接执行；同一 chat 的不同问题可以路由到不同真实 datasource。 |

### 3.1 当前 dataease / dmgt_table 的正确理解（2026-05-09 更正）

| 层级 | 表 / 数据 | 当前含义 | 对 SQLBot 的作用 |
|---|---|---|---|
| 目录数据源 | `dmgt_data_source_config.id = 3`，名称 `dataease` | 一个 MySQL 物理数据源，里面存放中台目录、权限、表登记等管理数据。 | SQLBot 不应把 `dataease` 物理库里的所有系统表都当作业务问数表。 |
| 业务目录 | `dmgt_category` | 中台的数据目录/资源表，当前约 3307 行，其中一部分能通过 `dmgt_table.category_id` 映射到物理表。 | 只作为业务名称、英文名、描述、审批状态、挂载状态和权限资源 ID 的补充信息；不能直接当作 SQLBot table。 |
| SQLBot schema 范围 | `dmgt_table` 中可执行的物理表 | 当前接口以 `dmgt_table` 为主表取数，只返回已登记物理表；不把没有物理表映射的 `dmgt_category` 返回给 SQLBot。 | LLM 看到的是可以生成 SQL 的表结构；是否允许查询数据交给权限 Gate 判断。 |
| 物理表映射 | `dmgt_table.category_id = dmgt_category.id` | `dmgt_category.id` 是中台资源 ID；`dmgt_table` 负责把资源 ID 映射到真实物理表名和真实数据源 ID。 | SQLBot 生成/执行 SQL 时必须使用 `dmgt_table.table_name` 和 `dmgt_table.data_source_id`，不能直接用目录名称执行。 |
| 字段目录 / 字段结构 | `dmgt_table_field.table_id = dmgt_table.id`，或真实库 JDBC 元数据 | 提供物理表字段名、类型、说明。 | 没有字段结构时，LLM 无法稳定生成 SQL；必要时继续使用真实库元数据兜底。 |
| 权限资源 | `dmgt_role.resource_id = dmgt_category.id`，`dmgt_user_role.role_id = dmgt_role.id` | 权限判断针对目录资源/表资源，而不是只针对物理表名。 | 表权限接口应先把 SQL 涉及的物理表反查到 `category_id`，再按用户角色判断 OWNER/READER/OPERATOR 等权限。 |

当前更正后的理解：

```text
dataease 数据源
  -> dmgt_table 保存 SQLBot 可执行的物理表登记
  -> 使用 dmgt_table.category_id 关联 dmgt_category.id 补充业务目录信息
  -> 通过 dmgt_table.data_source_id 找到真实数据源
  -> 通过 dmgt_table.table_name 找到真实物理表
  -> 通过 dmgt_table_field.table_id 或 JDBC 元数据拿字段结构
```

对应验证 SQL：

```sql
SELECT
  c.id AS category_id,
  c.name AS category_name,
  c.en_name,
  c.level,
  c.status,
  c.mount_status,
  c.approval_status,
  t.id AS table_id,
  t.table_name,
  t.data_source_id
FROM dmgt_table t
LEFT JOIN dmgt_category c
  ON c.id = t.category_id
 AND c.deleted = 0
WHERE t.deleted = 0;

-- 只有 dmgt_table 中登记的物理表会进入 SQLBot M-Schema。
```

注意：此前容易误解为“把 `dmgt_category` 的目录资源全部返回给 SQLBot”。正确理解是：SQLBot 原生会把远程接口返回的 `tables/fields` 直接拼成 M-Schema，因此这里必须返回真实可执行物理表结构。`dmgt_category` 只是补充表业务描述和权限资源 ID；没有 `dmgt_table` 映射的 category 不能直接进入 SQLBot schema。

### 3.2 数据目录接口目标取数逻辑（2026-05-08 补充）

目录接口目标是返回“SQLBot 可生成 SQL 的真实物理表结构”，不是返回 `dmgt_category` 资源目录全集，也不是返回物理库的所有系统表。

| 信息类型 | 来源表 | 过滤 / 关联方式 | 返回给 SQLBot 的用途 |
|---|---|---|---|
| 物理表结构 | `dmgt_table` | 以 `dmgt_table` 为主表；逻辑删除仍按 Mapper 规则排除。 | 提供真实 `table_id`、`table_name`、`data_source_id`，用于生成和执行 SQL。 |
| 业务目录补充 | `dmgt_category` | `dmgt_category.id = dmgt_table.category_id`。 | 提供业务名称、英文名、描述、审批状态、挂载状态和权限资源 ID；不单独作为 SQLBot table 返回。 |
| 字段结构 | `dmgt_table_field` | `category_id = dmgt_category.id`、`table_id = dmgt_table.id`、`deleted = 0`、`status = 'ENABLED'`。 | 提供字段名、别名、类型、长度、备注、排序、内容可见性等元数据，优先作为 SQLBot schema 字段来源。 |
| 权限关系 | `dmgt_user_role` + `dmgt_role` + `dmgt_category` | `dmgt_user_role.role_id = dmgt_role.id`，`dmgt_role.resource_id = dmgt_category.id`，并匹配当前 `tenant_id`、`user_id`、`role_type IN ('OWNER','READER','OPERATOR')`、未删除状态。 | 权限接口判断当前用户是否可查询 SQL 涉及的表资源。 |

字段结构以 `dmgt_table_field` 为准。当前 data 模块代码中的 `TableFieldDO` 明确绑定 `dmgt_table_field`，并且已有 `TableFieldService.listByTableId`、`TableFieldDao.selectByTableId` 等能力可直接复用。`dmgt_table_field` 同时带有 `category_id`、`table_id`、字段别名、字段备注、启用状态、排序和 `content_visible`。只有该表字段缺失时，再用真实库 JDBC 元数据兜底。

字段返回策略：默认只返回 `status = 'ENABLED'` 的字段。`DISABLED` 字段不进入 LLM schema。`content_visible` 的具体枚举需要以后端约定为准；在未确认前，应按保守策略处理，不把明确不可见内容字段提供给模型生成查询。

当前落地状态：中台 `SqlbotDatasourceController` 已按上述链路改造，接口以 `dmgt_table` 为主表获取已登记物理表，再关联 `dmgt_category` 补充业务目录信息，最后通过 `TableFieldService.listByTableId` 获取字段。接口仍保留 SQLBot 原本需要的 `tables[].name/comment/fields[].name/type/comment` 字段，并额外返回 `categoryId`、`categoryName`、`tableId`、字段 `alias` 等中台元数据，便于后续权限校验和排查。

### 3.3 绕开 SQLBot 原测试连接的设计说明（2026-05-09 补充）

SQLBot 原有流程在选择本地数据源后，会先调用 `datasource/check` 测试连接，确认本地 `core_datasource` 中的连接配置可用，再进入问数流程。这个逻辑适合 SQLBot 自己维护数据源的场景，但不适合当前中台接入模式。

当前中台模式采用“运行时虚拟 Assistant + 中台目录接口”的方式，不把中台数据源长期复制到 SQLBot 本地库。前端进入问数页时，`Assistant.type = 1` 表示远程 Assistant / 中台虚拟 Assistant，`ChatCreator.vue` 会直接创建 chat，不调用 `datasource/check`。这样可以避免把中台 `datasourceId` 当成 SQLBot 本地 `core_datasource.id` 去查，导致“数据源连接无效”。

该绕开并不降低权限安全性，原因如下：

| 点位 | 原测试连接能解决什么 | 当前中台模式如何处理 |
|---|---|---|
| 数据源是否能连通 | 只能证明数据库账号、地址、驱动可用。 | 中台目录接口负责提供运行时连接信息；连接失败仍会在 SQLBot 执行 SQL 时暴露为执行错误。 |
| 用户是否有表数据权限 | 不能解决。测试连接只验证数据库连接，不知道用户问题最终涉及哪些表。 | Gate 1 在 `check_sql` 后校验生成 SQL 涉及表；Gate 2 在最终 `execute_sql` 前二次校验。 |
| datasourceId 是否有效 | 原逻辑只认识 SQLBot 本地 datasourceId。 | 中台模式使用中台 datasourceId，由中台目录和权限接口解释。 |
| 无权时如何拦截 | 原测试连接没有无权表和申请入口概念。 | 权限接口返回 `deniedTables` 与 `applyUrl`，SQLBot SSE 返回 `permission_denied`，前端展示申请入口。 |

当前安全边界必须保持为：**SQLBot 可以拿到用于构建 schema 的真实物理表元数据，但只要 Gate 1 或 Gate 2 判断无权限，就不能执行 SQL。** 因此，不建议通过“不返回连接 URL/密码”来表达无权限；这会让 SQLBot 在相关性判断和 SQL 生成阶段失去必要上下文，也无法给出具体应申请哪些表。真正的阻塞点应放在 SQL 生成后、执行前。

## 4. 中台核心接口职责

| 接口 | 职责 | 可返回 | 不应返回 / 注意 |
|---|---|---|---|
| `GET /openapi/sqlbot/datasources/query` | 返回 SQLBot 可生成 SQL 的真实物理表结构，用于构建问数上下文。 | 数据源 id/name/type、host/port/database/schema、目录 id/name/enName/remark、物理表 tableId/tableName、字段名/别名/类型/说明、必要连接信息。 | 不返回未映射物理表的 category 资源；不返回 token、真实账号口令说明文档值、无关系统配置。密码如因 SQLBot 直连必须返回，只允许运行时内存使用，不得在 SQLBot 落库或日志输出。 |
| `POST /openapi/sqlbot/table-permissions/check` | 校验当前用户是否有 SQL 中相关表的数据查询权限。 | `allowed`、无权表 `deniedTables`、`tableId`、`categoryId`、`categoryName`、拒绝原因、申请入口 `applyUrl`。 | 不能只根据前端选择放行；不能在权限服务异常时默认放行。当前是表级校验，不是 SQL 字段级校验。 |

当前表权限接口落地状态：中台 `SqlbotPermissionController` 接收 SQLBot 传入的 `datasourceId` 和表名列表。每张表先按 `dmgt_table.data_source_id + table_name` 定位物理表，大小写不一致时做一次忽略大小写兜底；再确认物理表能关联到 `dmgt_category`；最后通过 `dmgt_user_role.role_id = dmgt_role.id`、`dmgt_role.resource_id = dmgt_category.id` 校验当前租户、当前用户是否拥有 `OWNER/READER/OPERATOR` 任一表级角色。所有表都通过时 `allowed=true`，任一表失败时返回 `allowed=false` 与无权表明细，权限不足原因为 `no_table_permission`。

## 5. 现有问题与待办

| 优先级 | 问题 | 影响 | 处理方向 |
|---|---|---|---|
| P1 | 当前只做表级权限，不做字段级 SQL 权限 | 用户可能只具备部分字段权限，但 SQLBot 暂按表级角色放行 | 后续如要精确到字段，需要解析 SQL select/join/filter 涉及字段，再另行恢复字段权限模型。 |
| P2 | 申请入口弹窗联动需要联调验证 | 用户无权时 SQLBot 已能展示申请按钮，并在中台嵌入模式下请求打开申请弹窗 | 用真实无权表点击“申请权限”，确认中台弹窗预填当前用户和资源，并可提交审批。 |
| P1 | 数据目录接口依赖真实库元数据读取 | 表多或连接慢时可能导致 SQLBot 拉目录超时 | 增加缓存、分页/按需拉取、或中台定时同步元数据。 |
| P1 | 表名大小写 / schema.table 解析 | 权限误判或 SQL 生成不稳定 | 统一 SQLBot 解析结果与中台表名规范。 |
| P1 | 目录可见范围与权限范围需要明确 | 用户可见结构但不可查数据，前端体验需解释清楚 | 文案和 SSE 事件中区分"无相关表"与"相关但无权限"。 |
