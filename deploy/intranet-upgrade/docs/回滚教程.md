# 六月定向升级回滚

先暂停问数入口，关闭自动同步并等待中台批次、PG `pending/running` 任务结束，再停止新 SQLBot 与 data-server。关闭浏览器不会停止后台任务。

保留故障日志时去除 Token、密码和业务数据。恢复前核对备份和镜像完整 ID，不使用可能已改变的 `latest`。

## 已验证的迁移关系

六月源码 `eec1a674` 的 Alembic head 为 `8ff90df7871d`，本包新增 `a6e066b1c001`（066），只新增三张索引表及索引/pgvector扩展。旧应用的 Alembic 不认识新 revision，所以**只换旧镜像不一定能启动**。

仅当升级前确认为 `8ff90df7871d`、升级中仅执行066、没有其他迁移时，可使用本包新镜像和原连接配置，把版本记录标回旧值，保留三张新增表。以下操作由授权部署人员在应用停机、备份确认后执行；它更新 Alembic 版本表，不删除业务数据。

```bash
cd "$DEPLOY_DIR"
# 此时原Compose仍指向本包新镜像。若使用override，需要加上同一override参数。
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" run --rm --no-deps \
  --entrypoint alembic sqlbot-backend current
# 必须先确认输出为 a6e066b1c001，且原备份记录确为8ff90df7871d
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" run --rm --no-deps \
  --entrypoint alembic sqlbot-backend stamp 8ff90df7871d
```

本回滚路径做过隔离 PG 验证：版本可标回旧值，新索引表保留、旧数据保留。`stamp` 只改变版本记录，不会撤销 SQL；它不能用于掩盖未知或失败的迁移。如果实际原 revision 不同、还有其他迁移、迁移中断或备份来源不明，停止上述命令，由维护人员依据迁移链与备份制定恢复步骤。

随后恢复旧 JAR、旧中台静态目录、原 nginx/Compose/env，以及原两份镜像 ID。保持原项目名和数据卷，按原顺序启动 data-server、SQLBot 后端与前端；`nginx -t` 通过后 reload。不要执行 `down -v`、删除新增索引表或导入整库初始化 SQL。

MySQL `dmgt_index_sync_control` 保留，旧六月应用忽略它。重新部署新版本前再次确认自动同步配置为关闭。恢复六月应用后，问数会恢复旧的在线表向量化/较慢召回和旧界面。

## 保留新表后再次升级

如果曾按上述步骤 `stamp` 回六月版本，新表仍在。**此时不能直接让066再次 CREATE 同名表。** 应在停机下由部署方对照本包066迁移，检查三表的列类型、唯一约束、外键及索引都完整一致，检查实际模型版本及任务状态，并核对上次回滚记录。

确认三表完整且迁移本身未撤销后，使用本包镜像执行 `alembic stamp a6e066b1c001`，再启动新版本。结构不完整或不同则停止，不能仅凭表名存在就 stamp。不要用删表重建解决而丢失同步记录。

数据库快照恢复属于另一条回滚路径，可能丢失快照后的写入，必须由现场备份负责人确认；本包不自动执行整库恢复。
