# 六月版 SQLBot 定向升级操作教程

本包状态为 **待联调验收**。可以在维护窗口按本教程安装并验收；不能据此认定已通过真实内网问数。当前开发环境曾出现中台认证 401，本包没有绕过认证，现场必须验证有效账号的完整链路。

## 1. 本次换什么

| 对象 | 操作 |
|---|---|
| SQLBot 后端、前端 | 导入本包两个 Linux amd64 镜像，在原 Compose 项目中更新镜像 |
| 中台 data-server | 替换六月源码定向补丁 JAR，保留 JVM、profile、Nacos、数据库配置 |
| 中台前端 | 替换为六月源码适配静态包，新增问数索引管理入口 |
| 中台 nginx | 合并 `/sqlbot-app/`、`/api/v1/` 代理与 SSE 设置 |
| SQLBot PG | 已验证 `8ff90df7871d → a6e066b1c001`，新增三个表 |
| 中台 MySQL | 仅新增 `dmgt_index_sync_control`，不改原业务表 |

不升级 PG/MySQL/Redis/Nacos/system-server，不扫描或更改被问数的物理业务库。不使用当前合并 master 后的中台 JAR。本包 JAR 基于 `4208811f`，中台静态包基于 `d3b41fee`；精确补丁、镜像 ID、模型指纹见 `release-manifest.json`。

六月版没有后来的整套数据源管理页面，本包使用独立的“问数索引管理”页面，地址 `/dataresource/datasource`。智能问数页面右下角提供入口，须拥有 `dmgt:data-source:sync`。部署脚本不批量授权；菜单配置及权限授予沿用中台授权流程。

## 2. 上传、核对基线

将外层 ZIP 上传内网，解压到独立目录。不要解压到原应用目录。以下命令均在 Linux 执行；先把路径变量替换为现场真实值。

```bash
cd /srv/releases/sqlbot-intranet-upgrade-20260909-linux-amd64
sha256sum -c SHA256SUMS
# 或 sh scripts/verify-package.sh
```

外层 ZIP 的 SHA256 在同名 `.sha256` 文件中。先校验再操作。包内不含数据库备份和真实环境配置。

镜像清单同时记录构建机的镜像 ID 和 `configDigest`。使用传统镜像存储的旧 Docker，导入后显示的 ID 可能对应 `configDigest`；构建机使用 OCI 索引摘要，两者显示不同不等于镜像损坏。核对标签、架构和包内摘要，不能只比较短 ID。

由维护人员确认并填写（示例路径不是现场既定路径）：

```bash
export DEPLOY_DIR=/srv/sqlbot
export COMPOSE_FILE="$DEPLOY_DIR/docker-compose.host.yml"
export COMPOSE_PROJECT=现有项目名
export DATA_JAR=/srv/data-server/yudao-module-data-biz.jar
export DATA_SERVICE_UNIT=现有data服务名.service
export PLATFORM_STATIC_DIR=/srv/nginx/html/platform
export MYSQL_DEFAULTS_FILE=/受控目录/mysql-readonly.cnf
export MYSQL_DATABASE=实际中台元数据库名
export PG_CONTAINER=现有PG容器名
export PG_USER=现场检查账号
export PG_DATABASE=sqlbot
sh scripts/preflight.sh
```

MySQL 凭据文件由授权运维准备，权限设为 600，不随离线包传播。PG 如果不是 Docker，用现场 `PGSERVICE` 和 `.pgpass/PGPASSFILE`，不要在命令行写密码。只读检查账号和运行服务账号可能不同，检查结果不代表服务账号拥有 DDL 权限。

原项目名可通过 `docker compose ls` 或原容器标签 `com.docker.compose.project` 查询。原目录、服务名、静态目录从既有运维记录和 nginx 配置核对。脚本按 Compose v2 + systemd 编写；现场使用 `docker-compose`、Supervisor 或启动脚本时，由运维逐项等效检查，不要照搬示例服务名。

预检对不同架构、PG 大版本、MySQL 系列和未知 Alembic 起点停止。现有依赖不符合实测范围时先做兼容验证，不能为了通过检查直接升级基础服务。还需确认 Docker 数据盘及备份盘空间，脚本的 12GiB 只是应用升级最低余量。

## 3. 备份并暂停问数入口

先保留以下对象：

- 两个旧镜像的完整 ID、原 Compose 项目名、Compose 和 env；不要只记可能变化的 `latest` 标签。
- 原 data-server JAR、启动命令/JVM参数、profile、Nacos配置版本。
- 原中台静态目录及 nginx 配置。
- 中台 MySQL 与 SQLBot PG 的一致性备份，以及 PG 当前 Alembic revision。

由获授权账号或既有备份平台完成数据库备份，并确认可恢复。备份含凭据时使用受限权限目录，禁止写进普通发布日志。

```bash
export BACKUP_DIR=/srv/backups/sqlbot-20260909
umask 077
mkdir -p "$BACKUP_DIR"
cp -a "$COMPOSE_FILE" "$BACKUP_DIR/"
# 原env、JAR、nginx和静态目录按核实路径备份
cp -a "$DATA_JAR" "$BACKUP_DIR/yudao-module-data-biz.jar"
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" images -q
# 对查出的两项ID分别执行docker image inspect，记录.Id；必要时docker save备份
```

使用现场维护方式暂停问数入口，等待现有请求结束。如果已试装过本功能，先关闭自动同步，确认 PG 无 `pending/running` 任务、中台批次也已结束。然后停止待替换的应用，数据库基础服务继续运行。不要执行 `docker compose down -v`。

## 4. 中台调度表及 data-server

`database/mysql-index-sync-control.sql` 只含一条 `CREATE TABLE IF NOT EXISTS`。目标是**中台元数据库**，不是名称相似的业务库，也不是 SQLBot PG。不执行历史整份 DDL，不执行 `ALTER TABLE dmgt_table_relation`，没有 DM 脚本。

服务在首次访问同步存储（包括服务端调度检查）时探测表结构。表不存在且账号有 `CREATE TABLE` 权限时自动创建；已有兼容表直接读写；已有不兼容表报错，不自动 ALTER、删表或覆盖数据。

服务账号没有建表权限时，由授权部署流程执行单独 SQL，例如由数据库维护人员通过既有平台提交文件。普通业务操作人员不需要直接连接数据库。若选择命令行执行，使用现场受控凭据文件及明确的目标库。

**保留旧配置很关键：本包不携带 `application-local/dev/prod` 等环境文件。** 如果原配置只打在旧 JAR 内，先从备份 JAR 提取实际使用的配置到受限外部目录，再替换 JAR。例如：

```bash
mkdir -p /srv/data-server/config
# 先列名称，确认扩展名和实际profile，不输出配置内容
unzip -Z1 "$BACKUP_DIR/yudao-module-data-biz.jar" | \
  sed -n '/^BOOT-INF\/classes\/application.*\.ya\?ml$/p'
# 将下例文件名换成上一步核实的原profile文件
unzip -p "$BACKUP_DIR/yudao-module-data-biz.jar" \
  BOOT-INF/classes/application-prod.yaml > /srv/data-server/config/application-prod.yaml
chmod 600 /srv/data-server/config/application-prod.yaml
test -s /srv/data-server/config/application-prod.yaml
```

如果现场已有外部文件/Nacos，继续使用它们。提取的文件不应覆盖现有外部配置。旧公共配置如有现场特有修改，也要纳入对照；不要用新包示例替换完整旧配置。

在原 profile 或 Nacos 合并唯一必需新增项：

```yaml
data:
  sqlbot:
    index-api-base-url: http://实际SQLBot服务器:8011/api/v1
```

替换前停止原 data-server，备份确认后复制本包 `platform/yudao-module-data-biz.jar` 到原 JAR 路径。沿用原启动方式、JVM参数、active profile 和 Nacos；需要外部配置时，在原 `java -jar ...` 的应用参数后追加 `--spring.config.additional-location=file:/srv/data-server/config/`，不要省掉原有参数或改动其他服务。

启动后检查新增接口是否存在、正常鉴权，特别是 `/openapi/sqlbot/datasources/{id}/embedding-metadata` 和 `/admin-api/dmgt/data-source/index-sync`。未登录、无同步权限、租户不匹配必须拒绝。不要增加宽泛的匿名放行规则。

中台一键/定时任务复用既有 OAuth2 RPC，以保存配置的用户权限运行；不保存浏览器 Token。依赖原 system-server/Redis/Nacos 链路可达。停用该用户或撤销同步权限应停止后续自动执行。

## 5. SQLBot 两个镜像

```bash
docker load -i images/sqlbot-images.tar
```

将 `config/sqlbot-env.additions.example` 的功能开关合并到**原** env，保留数据库密码、SECRET_KEY、认证 Redis 逻辑 DB、Nacos/网关地址、模型配置及数据卷。模型已经在镜像 `/opt/sqlbot/models` 中，无需下载或 pip 安装。原 Compose 如挂载同名模型目录，会遮住镜像模型，需核对该挂载与模型指纹，不要删除原目录。

六月包为 host 网络：API 8011，微应用静态服务 5173，原 MCP/图表服务使用 8012。若现场端口不同，沿用实际端口并同步调整代理。`PLATFORM_DATASOURCE_BASE_URL` 指向能访问 `/openapi/sqlbot/...` 的 data-server；认证基址和认证 Redis 则沿用中台认证部署，不能都随意填成同一端口。

在**原 Compose**仅将两个 image 改为：

```yaml
sqlbot-backend:  # 此处展示服务与镜像对应关系，不是完整Compose
  image: sqlbot-cx-backend-host:intranet-20260909
sqlbot-frontend:
  image: sqlbot-cx-frontend:intranet-20260909
```

不要改网络、卷、项目名。推荐直接修改原 Compose 两行，避免后续忘记 override 文件。若使用包内 override，今后所有 Compose 命令都必须带同一组 `-f` 文件。

```bash
cd "$DEPLOY_DIR"
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" up -d --no-deps sqlbot-backend
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" logs --tail=100 sqlbot-backend
```

首次启动自动执行 Alembic。预检通过的六月起点只有新增 066 迁移；应看到 `a6e066b1c001` 和以下三表：

- `platform_table_embedding`：完整规范化元数据、哈希、有效状态、模型版本。
- `platform_table_embedding_chunk`：每表多个文本片段和 `vector(768)`。
- `platform_embedding_sync_job`：持久化快照、任务进度及有限错误摘要。

PG 运行账号须具备执行迁移所需的 DDL 权限；安装 pgvector 扩展可能需要更高权限。应用不能绕过这些权限。缺扩展文件时走数据库授权维护流程，不更换 PG 数据目录或跨大版本换镜像。

主问数服务保持单实例、单 worker。待后端健康后再启动前端：

```bash
docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" up -d --no-deps sqlbot-frontend
```

## 6. 中台前端及 nginx

将 `platform/platform-frontend.zip` 解压到新的版本目录，根目录应直接有 `index.html` 和资源目录。保留旧目录，按既有发布方式切换 nginx root 或符号链接，不原地删除旧资源。旧浏览器标签需要刷新，必要时清理浏览器缓存并重新登录。

把 `config/nginx-sqlbot.locations.conf` 合并到现有中台 server 块；已有同名 location 时编辑原段，不能重复定义。示例 `127.0.0.1` 只适用于同机部署；分机替换为实际 SQLBot 地址。检查 `/api/v1/` 是否已被其他应用占用，有冲突先处理，不能覆盖别的服务。

- 页面 `/sqlbot/chat/index` 属于中台 SPA。
- `/sqlbot-app/` 转发到 SQLBot 前端 `5173/sqlbot/`。
- `/api/v1/` 转发到 SQLBot 后端 8011；每一层代理都关闭 SSE 缓冲、缓存。
- `/admin-api/`、其他系统、图片等现有代理保留。

```bash
nginx -t
# 仅在上一步通过后，按现场方式reload
nginx -s reload
export PUBLIC_ORIGIN=https://实际中台域名
sh /srv/releases/sqlbot-intranet-upgrade-20260909-linux-amd64/scripts/verify-deployment.sh
```

若 nginx 在容器内，用现场容器执行等效检查/reload；不要启动第二套 nginx。

## 7. 首次同步与验收

使用有同步权限的管理员登录，访问 `/dataresource/datasource`，点击“一键同步全部”，首次默认不勾选强制重建。索引范围是该数据源在中台**已登记**的完整结构，包括未上线/未挂载的注册表；当前用户没有查询授权也不影响管理员建索引。问数时仍使用当前租户已上线、已审批、已挂载的目录并执行原权限链路，索引不授予权限。

六月版未登记物理表/字段时，本功能不代替现有登记流程。没有字段的表会明确失败并保留旧索引，不会静默扫描业务库。六月结构没有的表说明、关联数据按缺失处理，关系为空。

记录下面的实际结果，全部关键项通过再开放入口：

1. 首次同步产生新增；再次同步主要为跳过；修改一张已登记表说明/字段后只更新相应表；全覆盖不代表每次重算。
2. 同源重复提交复用活动任务；刷新页面能恢复进度；单表失败不发布半张表向量，旧版本保留；删除注册记录后旧索引失效。下线但仍登记的表可保留索引，问数目录过滤必须排除它。
3. 有权账号提出真实问题，完成选表、权限校验、执行及结果展示；无权账号拒绝后没有 SQL 执行。401 必须显示认证失效，不能伪装成具体无权表。
4. 跨 schema 同名表正确区分；不同物理源的关联查询被拒绝；Gate 1/Gate 2 拒绝不展示“查询成功”。
5. 阶段清单默认展开，服务真实推进；成功且结果加载后收起，失败保留；停止显示“已停止接收”；SSE 事件逐条到达，不是结束后一次出现。
6. 在代表性真实问题集记录目录加载、问题向量化、PG召回、LLM选表、生成SQL、执行及总耗时。不能用本包 Mock 耗时或传输测试代替 P50/P95、95%覆盖率目标。

先验收手动同步，再设置每日自动同步时间。默认关闭，建议初次 22:00 北京时间，默认不强制重建。关闭浏览器不影响后台；当日服务恢复后已过执行时间且尚未执行会补跑一次。关闭开关仅影响后续任务，现有任务应等其结束。

## 8. 常见问题

| 现象 | 检查 |
|---|---|
| 没有索引入口 | 是否部署六月兼容静态包、是否拥有 `dmgt:data-source:sync`；直接路径不代替权限 |
| 部分失败/缺少字段 | 中台登记字段是否完整；不会自动读业务数据补全 |
| 索引服务暂不可用 | data-server 到8011、API基址、SQLBot启动日志、OAuth2/Redis、租户与同步权限 |
| Invalid or expired platform access token | 原中台认证Redis地址、DB索引、key前缀、有效期、用户类型及tenant-id；使用新登录验证，不能关闭Gate绕过 |
| Unknown column is_default/source | 可能误部署当前开发JAR；确认本包JAR哈希和六月基线，不继续运行无关DDL |
| 阶段停留很久 | 查看分段日志与SSE是否缓冲；进度卡改善反馈，不承诺LLM速度提升 |
| 回滚旧镜像报找不到revision | 先读《回滚教程》，不能直接stamp未知版本 |

本包不携带生产账号、真实数据库配置、业务数据或旧模型服务密钥。外部配置与数据库备份的现场保全由原维护流程负责。
